GitHub(github.com)는 소프트웨어 소스 코드를 저장·공유·협업하는 세계 최대의 개발 플랫폼입니다. 이 보고서는 GitHub가 무엇이며 왜 중요한지, 누가 운영하는지, 어떻게 사용하는지, 그리고 처음 접할 때 반드시 알아야 할 용어를 정리합니다.

작성 기준일: 2026년 9월 24일 · 수치 출처: GitHub Octoverse 2025 및 공개 통계 (본문 각주 참조)

1. GitHub란 무엇인가

GitHub는 Git이라는 버전 관리 도구를 기반으로 만들어진 웹 기반 코드 호스팅·협업 서비스입니다. 개발자는 자신의 코드를 GitHub에 올려 두고(저장), 변경 이력을 추적하며(버전 관리), 다른 사람과 함께 수정·검토합니다(협업). 오늘날 오픈소스 소프트웨어 대부분과 수많은 기업의 내부 코드가 GitHub 위에서 관리됩니다.

비유로 이해하기 — "코드를 위한 구글 드라이브 + 이력 관리 + 회의실"

구글 드라이브가 문서를 저장하고 공유하는 곳이라면, GitHub는 코드를 저장하고 공유하는 곳입니다. 다만 단순 저장에 그치지 않고, "누가 언제 어떤 줄을 왜 바꿨는지"가 모두 기록되고(이력 관리), 수정안을 제안하고 검토·승인하는 절차(회의실)까지 갖추고 있다는 점이 다릅니다.

구분GitGitHub

2. 운영 주체와 연혁

GitHub는 2008년 미국 샌프란시스코에서 톰 프레스턴-워너, 크리스 완스트라스, P. J. 하이엣, 스콧 채콘이 창업했습니다. 2018년 Microsoft가 약 75억 달러(주식 교환)에 인수하여, 현재는 Microsoft의 자회사로 독립 브랜드를 유지하며 운영됩니다.

연도주요 사건
2005리누스 토르발스가 Git 개발 (GitHub의 기반 기술)
2008GitHub 서비스 출시 — 웹에서 Git 저장소를 호스팅하고 "Pull Request"로 협업하는 방식 도입
2011~2015오픈소스 프로젝트 대거 이전, 사실상 오픈소스의 표준 거점으로 자리매김
2018Microsoft가 인수. 이후 무료 사용자에게 비공개(private) 저장소 무제한 개방
2019~2020GitHub Actions(자동화), GitHub Sponsors(후원), Codespaces(클라우드 개발환경) 출시
2021~2023GitHub Copilot(AI 코드 자동완성) 출시 — OpenAI 모델 기반, AI 개발 도구의 대표 사례가 됨
2025~2026AI 에이전트가 직접 Pull Request를 작성하는 "Copilot coding agent" 등 AI 중심 플랫폼으로 확장
주의 — Microsoft 소유이지만 Microsoft 전용은 아닙니다

인수 당시 "Microsoft 종속" 우려로 GitLab 등 경쟁 서비스로 이동하는 움직임이 있었으나, 이후 GitHub는 플랫폼 중립성을 유지했고 Google, Apple, Meta, 삼성 등 경쟁사 역시 GitHub에 공식 계정과 오픈소스 프로젝트를 운영합니다. Linux 재단 계열 프로젝트, Python, React, TensorFlow 등 핵심 오픈소스가 모두 GitHub에 있습니다.

수익 구조

  • 무료(Free): 공개·비공개 저장소 무제한, 개인·소규모 팀에 충분
  • Pro / Team / Enterprise: 고급 권한 관리, 보안 기능, 감사 로그, SSO 등 — 기업 고객이 주요 수익원
  • GitHub Copilot: AI 코딩 보조 구독 (개인·기업)
  • Actions / Codespaces: 자동화 실행 시간, 클라우드 개발 환경 사용량 기반 과금
  • Marketplace / Sponsors: 앱 판매, 개발자 후원 중개

3. GitHub의 중요성과 의미

3.1 "소프트웨어 세계의 공용 인프라"

오늘날 스마트폰 앱, 웹 서비스, 반도체 설계 도구, AI 모델에 이르기까지 거의 모든 소프트웨어는 오픈소스 라이브러리 위에서 만들어집니다. 그 오픈소스의 압도적 다수가 GitHub에 있으므로, GitHub는 사실상 전 세계 소프트웨어 공급망의 허브 역할을 합니다.

3.2 개발자의 "포트폴리오이자 이력서"

GitHub 프로필의 활동 기록(잔디밭 모양의 contribution graph)과 공개 저장소는 채용 시장에서 실질적인 실력 증명으로 쓰입니다. 어떤 프로젝트에 어떤 기여를 했는지가 투명하게 남기 때문입니다.

3.3 협업 방식 자체를 바꾼 플랫폼

GitHub가 대중화한 Pull Request 기반 코드 리뷰는 "먼저 제안하고, 검토받고, 승인 후 합친다"는 협업 문화를 표준으로 만들었습니다. 이 방식은 코드뿐 아니라 문서, 설정, 데이터, 심지어 법령·논문 협업에도 응용되고 있습니다.

3.4 AI 시대의 핵심 거점

GitHub에 쌓인 방대한 공개 코드는 AI 코드 생성 모델의 학습 기반이 되었고, 역으로 GitHub는 Copilot을 통해 AI가 개발자와 함께 일하는 첫 대규모 현장이 되었습니다. 2026년 현재 AI 에이전트가 작성한 Pull Request가 급증하며, GitHub는 "사람과 AI가 코드로 협업하는 공간"으로 재정의되고 있습니다.

비개발자에게도 의미가 있는 이유

GitHub는 코드가 아닌 것도 잘 다룹니다. 기술 문서 사이트(GitHub Pages로 무료 호스팅), 공개 데이터셋, 연구 자료, 설계 파일, 심지어 개인 블로그까지 GitHub로 관리·배포하는 사례가 많습니다. 반도체·하드웨어 분야에서도 펌웨어(예: Klipper, GRBL), 측정 장비 SDK, 회로 설계 파일이 GitHub에서 배포되므로, 사용법을 알아 두면 자료 확보와 문의(Issue)에 직접 도움이 됩니다.

5. GitHub 사용법

5.1 기본 작업 흐름 한눈에 보기

그림 1. 파일 수정 → commit(기록) → push(업로드) → Pull Request(검토·병합)의 기본 흐름

5.2 처음 시작하기 (계정 생성부터 첫 업로드까지)

  1. 계정 만들기 — github.com 접속 → Sign up → 이메일·비밀번호·사용자명 입력. 사용자명은 프로필 주소(github.com/사용자명)가 되므로 신중히 정합니다. 무료 플랜으로 충분합니다.
  2. 저장소(Repository) 만들기 — 우측 상단 "+" → New repository → 이름 입력 → Public(공개)/Private(비공개) 선택 → "Add a README file" 체크 → Create.
  3. 파일 올리기 (웹 방식) — 저장소 화면에서 "Add file → Upload files"로 드래그 앤 드롭. 코드를 몰라도 가능합니다. 하단에 변경 설명(commit message)을 적고 "Commit changes".
  4. 파일 올리기 (Git 방식) — Git을 설치한 뒤 터미널에서 아래 명령을 실행합니다. 반복 작업·대용량 프로젝트에 적합합니다. 
    git clone https://github.com/사용자명/저장소명.git   # 내려받기
cd 저장소명
# ... 파일 수정 ...
git add .                                   # 변경 파일 선택
git commit -m "측정 스크립트 추가"            # 변경 기록
git push                                    # GitHub로 업로드
  5. GitHub Desktop 활용 — 명령어가 부담스럽다면 무료 GUI 프로그램 GitHub Desktop을 설치하면 클릭만으로 commit/push/pull이 가능합니다. VS Code에도 Git 기능이 내장되어 있습니다.
  6. 협업 참여 — 남의 저장소에 기여하려면 Fork → 수정 → Pull Request 순서를 따릅니다. (6장 용어 참조)

6. 꼭 알아야 할 핵심 용어

아래 용어는 GitHub 화면과 대화에서 매일 등장합니다. 각 용어를 정의와 비유로 정리했습니다.

Repository (저장소)줄여서 "repo"

하나의 프로젝트를 담는 단위. 소스 코드, 문서, 이미지와 함께 모든 변경 이력이 들어 있습니다. Public(누구나 열람)과 Private(초대된 사람만)로 나뉩니다.

비유: 프로젝트 하나를 통째로 담은 "서류 캐비닛". 안에는 현재 문서뿐 아니라 과거의 모든 수정본이 함께 보관됩니다.

Commit (커밋)

변경 사항을 저장소 이력에 기록하는 행위, 또는 그 기록 하나하나. 각 커밋은 "무엇을 왜 바꿨는지" 메시지와 고유 ID(해시)를 가지며, 언제든 그 시점으로 되돌릴 수 있습니다.

비유: 게임의 "세이브 포인트". 잘못되면 이전 세이브로 돌아갈 수 있고, 세이브마다 메모가 붙어 있습니다.

Branch (브랜치)

본선(main)에서 갈라져 나온 독립적인 작업 줄기. 새 기능이나 실험을 본선에 영향 주지 않고 진행한 뒤, 완성되면 다시 합칩니다(merge).

비유: 원본 문서는 그대로 두고 "복사본에서 초안 작업"을 하다가, 완성되면 원본에 반영하는 것.

Merge (병합)

브랜치의 변경 내용을 다른 브랜치(주로 main)에 합치는 작업. 같은 줄을 서로 다르게 고쳤다면 충돌(conflict)이 발생해 사람이 선택해야 합니다.

비유: 두 사람이 따로 고친 문서를 한 문서로 합치기. 같은 문장을 다르게 고쳤으면 어느 쪽을 쓸지 정해야 합니다.

Fork (포크)

다른 사람의 저장소를 내 계정으로 통째로 복사하는 것. 원본을 건드릴 권한이 없어도 내 복사본에서 자유롭게 수정하고, 원본에 반영을 제안(Pull Request)할 수 있습니다.

비유: 남의 레시피를 내 노트에 옮겨 적어 내 식대로 개량하는 것. 개량본이 좋으면 원저자에게 "이렇게 바꿔 보시죠" 하고 제안할 수 있습니다.

Pull Request (PR, 풀 리퀘스트)

"내 변경 사항을 당신 저장소로 끌어당겨(pull) 주세요"라는 요청. 변경 내용을 줄 단위로 비교해 보여 주며, 검토자가 댓글·승인·수정 요청을 남기고 최종 병합합니다. GitHub 협업의 핵심 절차입니다.

비유: 수정 제안서 + 결재 요청. "이렇게 고쳤으니 검토 후 반영해 주세요."

Clone (클론)

GitHub의 저장소를 이력까지 포함해 내 컴퓨터로 통째로 내려받는 것. Fork가 "GitHub 안에서 내 계정으로 복사"라면 Clone은 "내 PC로 복사"입니다.

비유: 캐비닛 전체를 내 책상으로 복사해 오기.

Push / Pull (푸시 / 풀)

Push: 내 PC의 커밋을 GitHub로 올리기. Pull: GitHub의 최신 커밋을 내 PC로 가져오기. 팀 작업 시 "pull 먼저, 작업, 그다음 push"가 기본 습관입니다.

비유: Push는 "업로드", Pull은 "동기화(최신본 받기)".

Issue (이슈)

버그, 기능 요청, 질문, 할 일을 등록하는 티켓. 번호(#123)가 붙고, 커밋이나 PR과 연결되어 "이 수정으로 이슈 #123 해결"처럼 추적됩니다.

비유: 프로젝트의 "민원 접수 게시판" 겸 "할 일 카드".

README

저장소 첫 화면에 표시되는 소개 문서(README.md). 프로젝트가 무엇인지, 설치·사용법, 라이선스를 적습니다. Markdown 문법으로 작성합니다.

비유: 제품 상자에 붙은 "설명서 겸 안내문".

Star / Watch

Star: 관심 표시 겸 북마크. 스타 수는 프로젝트 인기의 척도로 쓰입니다. Watch: 해당 저장소의 이슈·PR 알림을 구독.

비유: Star는 "좋아요 + 즐겨찾기", Watch는 "알림 켜기".

GitHub Actions / CI

저장소에 push나 PR이 생길 때 자동으로 테스트·빌드·배포를 실행하는 자동화 기능. CI(지속적 통합)/CD(지속적 배포)를 GitHub 안에서 구현합니다.

비유: 서류가 접수될 때마다 자동으로 검사·복사·배송까지 해 주는 "무인 처리 라인".

GitHub Pages

저장소의 HTML 파일을 무료 웹사이트로 호스팅하는 기능. 정적 문서, 기술 보고서, 브라우저용 계산기·시각화 도구 배포에 널리 쓰입니다.

비유: 캐비닛 속 문서를 그대로 "온라인 전시관"에 걸어 두기.

흔한 오해 바로잡기
  • "Commit하면 GitHub에 올라간다?" — 아닙니다. Commit은 내 PC의 로컬 저장소에 기록하는 것이고, GitHub에 올리려면 Push를 해야 합니다.
  • "Fork와 Clone은 같다?" — Fork는 GitHub 서버 안에서 내 계정으로 복사, Clone은 내 컴퓨터로 복사입니다. 보통 Fork 후 Clone합니다.
  • "Pull Request는 Pull의 요청?" — 이름 때문에 헷갈리지만, 실제로는 "내 변경을 검토하고 병합해 달라"는 요청입니다. GitLab에서는 같은 기능을 "Merge Request"라고 부릅니다.
  • "Public 저장소는 누구나 수정할 수 있다?" — 누구나 볼 수는 있지만 직접 수정은 권한자만 가능합니다. 외부인은 Fork → PR로 제안만 할 수 있습니다.

7. 실무 활용 팁과 유의사항

7.1 시작할 때 권장 습관

  • 커밋 메시지는 "무엇을·왜" — "수정" 대신 "전압 프로브 오프셋 보정 로직 추가 (드리프트 문제 대응)"처럼 적습니다.
  • 작게, 자주 커밋 — 하나의 커밋에 하나의 의도. 되돌리기와 검토가 쉬워집니다.
  • .gitignore 설정 — 임시 파일, 대용량 측정 데이터, 비밀번호 파일은 저장소에 올리지 않도록 제외 목록을 만듭니다.
  • README를 먼저 — 목적, 실행 방법, 필요한 장비·라이브러리를 적어 두면 미래의 나와 동료 모두에게 도움이 됩니다.
  • 라이선스 명시 — 공개 저장소라면 MIT, Apache-2.0 등 라이선스 파일을 추가해 이용 조건을 분명히 합니다.

7.2 보안·기밀 유의사항

회사 자료를 올리기 전 반드시 확인
  • API 키, 비밀번호, 인증서는 절대 커밋하지 않습니다. 한 번 push된 비밀은 이력에 남아 삭제해도 복구될 수 있습니다.
  • 사내 기술 자료(공정 조건, 설계 데이터, 미공개 사양)는 회사 보안 정책에 따라 사내 Git 서버(GitHub Enterprise Server, GitLab 등)를 사용하는 것이 원칙입니다. 개인 GitHub 계정의 Private 저장소도 사규상 허용되지 않는 경우가 많습니다.
  • Public 저장소는 검색 엔진과 AI 학습 크롤러에 노출됩니다. 공개 전 내용을 한 번 더 점검하십시오.
